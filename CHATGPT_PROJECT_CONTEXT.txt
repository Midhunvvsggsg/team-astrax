1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
================================================================================
Project Name: AstraFlow Software
Team: team-astrax
Repository: https://github.com/Midhunvvsggsg/team-astrax

Business Context:
AstraFlow Software is a SaaS and services provider selling monthly/yearly
software subscriptions, add-ons, and products with multi-attribute variants.
Previously, recurring operations were broken:
- Subscriptions tracked in spreadsheets;
- Renewals forgotten or missed;
- Invoices created manually each month;
- Bank payments reconciled by manually matching statement lines;
- Financial metrics (MRR/ARR/Churn) calculated by hand on quarterly spreadsheets.

The Solution:
A resilient, unified, 100% offline-first web platform that handles the complete
subscription lifecycle:
- Product and variant catalog with customizable tax and pricing tiers;
- Quotation templates converting into enforceable subscription contracts;
- Idempotent recurring billing engine catching up on all past unbilled periods;
- Multi-method payments (Bank Transfer, Card, UPI, Cash) supporting partial payments;
- Heuristic bank statement CSV reconciliation engine;
- Live executive finance dashboard (MRR, ARR, overdue aging, collection rates);
- Isolated customer self-service portal;
- Automated daily background jobs (invoicing, renewals, expiry, reminders) with
  a persistent "Demo Clock" allowing fast-forwarding time during live hackathon demos.

2. TECH STACK & DESIGN PHILOSOPHY
================================================================================
Backend: Python 3.12+ / Django 5.x
Database: SQLite 3 (embedded in-process with WAL mode, sub-millisecond query latency)
Frontend: Django Server-Rendered Templates, Bootstrap 5 + custom utility theme,
          Chart.js (bundled locally, 100% offline-safe)
Validation: Dual-layer (Instant client-side feedback + strict server-side validation)
Design Principles:
1. 100% Offline-First: Zero external cloud APIs, zero CDN dependencies. If the venue
   Wi-Fi drops entirely, the entire application, seed data, and charts run locally.
2. Financial Precision: Decimal fields used everywhere for monetary calculation.
   Zero float rounding errors. Decimal rounding strictly enforced to 2 places.
3. Strict Query Scoping: Customer-facing endpoints strictly filter by request.user.
   ID enumeration attacks return HTTP 404 rather than HTTP 403.
4. Mathematical Bounding: Discounts and payments are capped to prevent negative
   invoice balances or overpayments.
5. Idempotent by Design: Physical DB composite unique constraints prevent double
   invoicing even under concurrent runs or network hiccups.

3. USER ROLES, AUTHENTICATION & SECURITY ISOLATION
================================================================================
Roles Matrix:
1. Admin (`role = 'admin'`, `is_superuser = True`, `is_staff = True`):
   - Unrestricted access across the system.
   - ONLY role authorized to create staff members, catalog products, variants,
     plans, taxes, discount rules, trigger manual daily automations, and manage
     the demo clock.
2. Staff (`role = 'staff'`, `is_staff = True`):
   - Operational team handling day-to-day sales and finance.
   - Can view and manage customers, quotations, subscriptions, invoices,
     payments, and upload bank statements.
   - Cannot create staff users or modify fundamental catalog pricing/tax models.
3. Customer (`role = 'customer'`, `is_staff = False`):
   - External clients logging into the dedicated Customer Portal (`/accounts/portal/`).
   - Can view ONLY their own subscriptions, lines, invoices, and verified payment history.
   - Can perform allowed plan actions (e.g. pause, resume, cancel) if permitted by plan flags.

Authentication & Password Security Rules:
- Email is the unique username identifier (case-insensitive normalized).
- Password Complexity Policy:
  * Minimum 9 characters (> 8 characters).
  * Must contain at least one uppercase letter [A-Z].
  * Must contain at least one lowercase letter [a-z].
  * Must contain at least one special character [!@#$%^&*(),.?":{}|<>].
  * Enforced on BOTH client (dynamic JS meter) and server (`clean_password` validator).
- Password Reset: Standard Django cryptographic token workflow. Uses console email
  backend (`django.core.mail.backends.console.EmailBackend`) for offline hackathon testing.
- Anti-Enumeration & Query Isolation:
  * In customer portal views, records are fetched with:
    `get_object_or_404(Invoice.objects.filter(customer=request.user), pk=pk)`
  * Attempting to guess another user's invoice ID returns HTTP 404 (Not Found),
    never leaking whether an invoice with that ID exists.

Default Demo Credentials:

- Operational Staff: `staff@brightloop.com` / `Staff@12345`
- Demo Customer: `acme@corp.com` / `CustomerPass@123`

6. SUBSCRIPTION & INVOICE LIFECYCLE STATE MACHINES
================================================================================

Subscription Lifecycle State Machine:
Valid States: Draft -> Quotation -> Confirmed -> Active -> Paused -> Closed

Transition Matrix:
- Draft -> Quotation: Triggered when quote is prepared and given an expiry date.
- Quotation -> Confirmed: Customer or staff accepts the proposal.
- Quotation -> Closed: Quotation rejected or expired without acceptance.
- Confirmed -> Active: Services are activated; next_billing_date is established.
- Active -> Paused: Temporarily suspended (ONLY allowed if plan.pausable == True).
- Paused -> Active: Resumed; billing dates re-aligned.
- Active -> Closed: Natural completion, cancellation, or early termination
  (Early termination ONLY allowed if plan.closable_early == True).
- Paused -> Closed: Terminated while paused.
- Active -> Active (Renewal): Explicit renewal (ONLY allowed if plan.renewable == True).

Status History Audit Trail:
Every transition creates an immutable `SubscriptionStatusHistory` record capturing:
`subscription`, `from_status`, `to_status`, `changed_by`, `changed_at`, `notes`.

Invoice Lifecycle State Machine:
Valid States: Draft -> Confirmed -> Paid (or Cancelled)
- Draft: Automatically generated by billing engine or manually drafted.
- Confirmed: Finalized and locked for delivery (sends email notice, sets `sent_at`).
- Paid: Triggered automatically when sum of approved `Payment.amount` >= `Invoice.total`.
- Cancelled: Allowed only from Draft or Confirmed before full payment is collected.

7. BILLING ENGINE, IDEMPOTENCY & DISCOUNT CALCULATION
================================================================================
Billing Engine Architecture (`invoicing/services.py: generate_invoices`):
1. Identification:
   - Queries all subscriptions where `status == 'active'` and `start_date <= as_of_date`.
2. Chronological Period Catch-Up:
   - For each subscription, identifies periods from `start_date` up to `as_of_date`.
   - Checks existing billed periods via `sub.invoices.values_list('period_start', flat=True)`.
   - Any missing historical period is billed in chronological order.
3. Dual-Layer Idempotency Guarantee:
   - Layer 1 (Software): Checks if `period_start` is already in the billed periods set.
   - Layer 2 (Database Constraint): `UniqueConstraint(fields=['subscription', 'period_start'])`.
   - Result: Running `generate_invoices()` 10 times consecutively produces 0 duplicate
     invoices, 0 phantom line items, and 0 overcharges.
4. Line Item Compilation:
   - Replicates active `SubscriptionLine` entries into `InvoiceLine`.
   - Line Total = `quantity * unit_price`.
   - Tax Calculation = `line_total * (tax.percentage / 100) + tax.fixed_amount`.
5. Automatic Discount Evaluation (`subscriptions/services.py: get_applicable_discounts`):
   - Validates:
     * `is_active == True`
     * `start_date <= billing_date <= end_date`
     * `usage_limit is None` OR `times_used < usage_limit`
     * Meets `min_purchase_amount` and `min_quantity` thresholds.
   - Computes eligible amount:
     * If `applies_to == 'product'`: only sums matching line items.
     * If `applies_to == 'subscription'`: sums all line items.
   - Mathematical Bounding:
     * Percentage discounts capped at 100%.
     * Fixed discounts bounded by eligible subtotal: `min(rule.value, eligible_amount)`.
     * Invoice totals can NEVER drop below $0.00.
   - Applied as a transparent negative invoice line item (`-Discount: <Rule Name>`).
   - Atomically increments `rule.times_used += 1`.
6. Payment Due Date Computation:
   - Configurable per subscription/plan: Immediate (0 days), Net 15 (+15 days),
     Net 30 (+30 days), Net 60 (+60 days).
   - Calendar-safe date arithmetic handling leap years and variable month lengths
     via custom `add_months()` helper.

8. BANK STATEMENT RECONCILIATION ENGINE
================================================================================
Architecture (`invoicing/models.py`, `invoicing/views.py`):
1. Ingestion:
   - Finance staff uploads bank statement CSV (`Date, Description, Amount, Reference`).
2. Duplicate Prevention:
   - Computes SHA-256 hash of `(date, amount, reference, description)`.
   - Pre-existing duplicate rows in the database are flagged `status = 'duplicate'` and ignored.
3. Automated Heuristic Matching:
   - High Confidence (`confidence = 'high'`):
     * Description or reference contains exact invoice pattern regex: `INV-\d{5}`.
     * Invoice status is `draft` or `confirmed`.
     * Statement row amount matches invoice remaining balance exactly.
     * Automatically transitions row to `auto_reconciled`, creates a verified `Payment`
       record, and marks the invoice `paid` if fully satisfied.
   - Medium Confidence (`confidence = 'medium'`):
     * Fuzzy match: Customer name matches description AND amount matches outstanding balance,
       OR invoice number matches but amount represents a partial payment.
     * Flagged as `status = 'needs_review'`.
     * Staff clicks "Approve Match" with one click to confirm.
   - Low / Unmatched (`confidence = 'low'`):
     * No invoice reference or customer identifier detected.
     * Staff can manually search invoices and bind reconciliation manually (`manual_reconcile`).

9. AUTOMATION SYSTEM & SIMULATED DEMO CLOCK
================================================================================
Daily Background Automation (`automation/services.py: execute_daily_jobs`):
Runs 5 automated enterprise jobs in atomic sequence:
1. Recurring Invoicing: Calls `generate_invoices(as_of_date)` to bill all due subscriptions.
2. Auto-Renewals: Detects subscriptions ending on or before `as_of_date` whose plans have
   `renewable == True`, automatically rolling their end dates and generating renewal quotes.
3. Auto-Expiry Closure: Detects expired subscriptions whose plans have `auto_close_on_end == True`
   and safely transitions their status to `closed`.
4. Automated Reminders:
   - Dispatches expiry notices 7 days before non-renewable contracts end.
   - Dispatches dunning notices for overdue invoices at 3 days, 7 days, and 14 days overdue.
   - Guaranteed single-send via database unique constraints on `Reminder`.
5. Month-End Reporting:
   - If `as_of_date` is the final day of a calendar month, automatically compiles and
     freezes the `MonthlyReport` financial snapshot.

The Demo Clock (`automation/clock.py`):
- Hackathon Problem: How do you show recurring billing, renewals, and overdue notices
  that naturally take 30 to 60 days to trigger in a 2-minute live demo?
- Solution: The `DemoClock` singleton (`id=1`).
- When `DEMO_MODE=1`, all system date calls route through `get_today()`, which checks
  the database-persisted simulated date.
- Operations UI (`/automation/`):
  * "Advance 1 Day" -> Fast-forwards clock by +1 day.
  * "Advance 1 Month" -> Fast-forwards clock by +30 days and executes daily jobs.
  * "Reset to Real Time" -> Synchronizes back to `datetime.date.today()`.
  * Demonstrates 3 full billing cycles in 30 seconds live in front of judges!

10. PERFORMANCE OPTIMIZATIONS & BENCHMARKS (5,000+ SUBSCRIPTIONS)
================================================================================
Performance Targets Met:
- Sub-60ms average server response time on pages listing 5,000+ subscriptions.
- Database query count per page view capped between 2 and 5 queries (zero N+1 queries).

Key Engineering Techniques:
1. ORM Optimization:
   - Heavy use of `.select_related('customer', 'plan')` on single-valued relations.
   - `.prefetch_related('lines__product', 'lines__variant', 'lines__tax')` on M2M/reverse FKs.
2. Database Indexes:
   - B-Tree indexes on all frequently filtered fields: `status`, `start_date`, `end_date`,
     `next_billing_date`, `issue_date`, `due_date`, `period_start`.
   - Composite index on `['customer', 'status']`, `['product_type', 'is_active']`.
3. Push Aggregations to the Database Engine:
   - The executive finance dashboard calculates MRR, ARR, collection rates, total revenue,
     and overdue buckets strictly using Django SQL expressions:
     `Sum(Case(When(...))), Count(...), Coalesce(...)`.
   - Never loops over QuerySets in Python memory.
4. Bulk Seeding:
   - `seed_demo` creates 5,000 subscriptions, 10,000+ lines, and 9,800+ invoices in ~35 seconds

Top 8 Judge Questions & Answers:

Q1: How do you guarantee billing idempotency? What happens if the job runs twice?
A: Idempotency is enforced at two distinct layers. At the database layer, a composite
unique constraint on (subscription, period_start) makes duplicate invoices physically
impossible. At the service layer, `generate_invoices()` pre-queries existing period
starts and skips already-billed periods. Running the engine twice produces zero duplicates.

Q2: How does your system handle catch-up for past unbilled periods or server downtime?
A: Rather than only billing for the current calendar day, `generate_invoices(as_of_date)`
detects all missed past periods since the subscription's start date (or last billed invoice)
and generates chronological invoices period-by-period until the subscription is caught up.

Q3: How do you guarantee customer data privacy and prevent cross-customer access?
A: We enforce strict query scoping on the server. In customer-facing views, queries
filter directly on `request.user` (e.g. `Invoice.objects.filter(customer=request.user)`).
If a customer tries to tamper with another customer's ID in the URL, the system returns
HTTP 404 (Not Found) rather than 403 (Forbidden), completely preventing ID enumeration.

Q4: How are discounts evaluated and what prevents negative invoice totals?
A: `get_applicable_discounts()` checks active status, date validity, remaining usage
limits, minimum quantities/purchase amounts, and scope (subscription vs. product).
In our mathematical service, percentage discounts are capped at 100% and fixed discounts
are bounded by the eligible subtotal, mathematically guaranteeing invoices can never
have negative totals.

Q5: Why SQLite instead of PostgreSQL for this hackathon?
A: SQLite delivers 100% offline-first resilience with zero external service dependencies
or cloud credential requirements. It satisfies all ACID constraints, runs embedded
in-process with sub-millisecond query latencies, and allowed us to seed 5,000 subscriptions
and 9,800+ invoices in ~35 seconds using chunked bulk operations.

Q6: How do you achieve sub-60ms page load speeds across 5,000+ active subscriptions?
A: We eliminated N+1 queries through strategic `select_related` and `prefetch_related`
joins, added composite database indexes across commonly queried foreign keys and date/status
fields, and computed financial totals (MRR, revenue, payments, amounts due) entirely in
database SQL aggregates using `Sum`, `Count`, and `Case/When`.

Q7: How are product variants priced and how does choosing a variant affect lines and invoices?
A: Each `ProductVariant` specifies an `extra_price` associated with an attribute
(e.g. Brand=Odoo adds $560.00). When added to a quotation template or subscription line,
the unit price automatically computes `product.sales_price + variant.extra_price` while
allowing operational staff to customize it if needed.

Q8: How does the system handle subscription expiry and plan lifecycle permissions?
A: Plans define granular boolean policy flags: `pausable`, `renewable`, `closable_early`,
and `auto_close_on_end`. The state machine rejects actions not permitted by the plan.
For automated lifecycle management, the `close_expired_subscriptions` management command
safely transitions active and paused subscriptions past their expiry date to `Closed`
if `auto_close_on_end` is enabled.
